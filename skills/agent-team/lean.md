# 省 token · 提质量（借鉴 ponytail、mattpocock/skills）

队长的上下文是全队最贵的资源：每一份汇报都落进去。成员的上下文其次。规则按「谁的窗口」分。

## 队长窗口

- **指针代替内容**：派工 prompt 只给路径（SPEC / 工单 / 收件箱 / 上游交接单），成员自己去读。禁止把 SPEC 或代码粘进 prompt。
- **汇报上限 200 字**：交接单路径 + 产出 / 偏差 / 风险三行。细节留在交接单里，队长按需再读。
- **只读三个字段**：收报后读交接单的 `deviations`、`risks`、`to-inbox`，其余不读。
- **一次派一波**：无阻塞的工单同时派出（`run_in_background: true`），避免串行等待时反复刷新上下文。
- **不重派已成功的人**：需要小改就把改动写进工单追加一张小工单派同一角色，附上游交接单路径。

## 成员窗口

- **先读三样再动手**：SPEC、自己的工单，运行 `python ~/.claude/team-board/msg.py inbox <subagent_type>` 读收件箱（每里程碑再查一次）；上游交接单只在工单 `blocked_by` 非空时读。**不通读全库**：按工单 `files` 定向 grep。
- **写代码用「懒惰资深」阶梯**，停在第一个成立的台阶：
  1. 这东西需要存在吗？推测性需求 → 不做，一句话说明。
  2. 代码库里已有？（helper / util / 类型 / 模式）→ 复用，写之前先找。
  3. 标准库能做？→ 用标准库。
  4. 平台原生能做？（CSS 代替 JS、DB 约束代替应用代码、硬件定时器代替软件延时）→ 用原生。
  5. 已装依赖能做？→ 用它；几行能做的事不加新依赖。
  6. 能一行写完？→ 一行。
  7. 才写最少的能工作的代码。
- **阶梯之前先读懂**：改之前把工单涉及的调用链追一遍；bug 修根因不修症状（先 grep 所有调用方）。
- **不做未要求的抽象**：单实现的接口、单产品的工厂、永不变化的配置项、"以后用"的脚手架，都不写。
- **刻意留下的上限**用注释标记：`// lean: 全局锁，吞吐不够再改按账号锁`。
- **非平凡逻辑留一个能跑的检查**：一个 `assert` 自检或一个最小测试，不建框架、不写逐函数套件。
- **输出**：代码优先，说明最多三行（跳过了什么、何时补上）。解释比代码长就删解释。
- **不许省的**：信任边界的输入校验、防数据丢失的错误处理、安全、无障碍基础、用户明确要求的东西。

## 写给 agent 的文档（skill / agent 定义 / CLAUDE.md）

- 主文件放**步骤**，参考资料放到旁边文件，用指针引用（本 skill 就是这样组织的）。每一行常驻内容每轮都在花 token。
- 每一步以**完成标准**结尾（可判定、要求穷尽："每个待改文件恰好属于一张工单"，而不是"理清工单"）。
- **正向措辞**：写要做的事，不写禁止的事（禁止句会把被禁行为拉进上下文）。硬红线才用禁止句，并配正向目标。
- 用模型已有的**引导词**（tracer bullet、竖切片、根因、YAGNI）代替长句描述。
- 环境能查到的（package.json 脚本、目录结构、`--help`）不写进文档；只写查不到的：不成文约定、取舍原因、坑。
- 每句问一遍：删掉它模型的行为会变吗？不变就删整句。

## 结算

验收时 `curl -s http://127.0.0.1:7788/snapshot.json`，报告 `totals.membersCost`、`totals.modelMix`、各部门 `cost`。对照成员上限；单个成员成本明显高于同档同事（如某 sonnet 成员 > 3× 同伴）时，查它的交接单：通常是通读全库或反复重试，下次在工单里收紧 `files` 与完成标准。
